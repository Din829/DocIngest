# DocIngest 使用ガイド（企業級）

## 30 秒で判断

DocIngest は **20+ 形式の文書 → Markdown 変換ライブラリ**。docling + litellm + Vision API の組合せで、PDF / Office / 音声 / 動画まで対応する。

**強い**: フォーマット網羅、Markdown 変換品質、Vision でのページ画像理解
**弱い**: 子プロセス・ログ・キャッシュの落とし穴、デフォルト設定がトークン浪費
（~~Azure OpenAI 非対応~~ は **2026-06-21 解決済み** — `AzureOpenAIProvider` 既存 + `docingest.azure`
プラグイン[azure_di 解析 / Azure AI Search export]+ 大型 PDF 用 `engine: vision_only`。§4.1 参照）

**Mplat ではどう使っているか**: worker プロセス内の子プロセス内で `outputs=["markdown"]` のみ取得。enrichment は全部捨てる。それでもいくつかの bug を踏みながら現状の形に至った（2026-05-25 時点で実 prod 動作確認）。

---

## DocIngest の機能マップ

```
入力ファイル (PDF/DOCX/PPTX/XLSX/MP3/MP4/...)
   ↓
docling 解析（文字 + 表構造 + メタ）
   ↓
Vision API（PDF ページ画像 / PPT スライド画像 / DOCX→PDF 画像）
   ↓
Markdown 生成
   ↓
（任意）enrichment:
   - chunking          → chunks.jsonl
   - chunking_assist   → LLM が境界推定 ★ LLM 呼出
   - knowledge_map     → 全文書俯瞰 + 検索ガイド ★ LLM 呼出
   - tags / aliases    → ファイル別タグ
   - quality_report    → 抽出品質スコア
   - run_log           → 実行履歴 .md
```

## Mplat が実際に使っているもの

| 機能 | 使っている？ | 理由 |
|---|---|---|
| docling 解析（→ Markdown）| ✅ | 核心 |
| Vision（PDF/PPT 画像認識）| ✅ | 図表理解に必須 |
| chunking | ❌ | Mplat が独自に sanitize+extract |
| chunking_assist (LLM) | ❌（**しかし default で動いてしまう**）| ↓ §4.7 |
| knowledge_map | ❌ | Mplat に SkillCatalog がある |
| refine / quality_report / run_log | ❌ | 運用レポート、不要 |
| incremental cache | ⚠️ | コンテナ再起動で消える、§4.8 |

`adapter.ingest(path, tenant_id, outputs=["markdown"])` で多くの reader を切れるが、**LLM 呼出は別レイヤー**で残るので env で明示的に止めること（§4.7 / §6）。

## 4. 企業級で踏む 8 課題

### 4.1 Vision の AOAI 非対応 ~~⭐ 今の痛点~~ → ✅ 解決済み（2026-06-21 追記）

> **⚠️ この節は 2026-05-25 時点の記録。以後 DocIngest 本体が更新され、もう痛点ではない**：
> - `AzureOpenAIProvider` は **既に存在する**（`providers.py`、litellm の `azure/<deployment>`
>   + `api_base` 経路）。下の「無い」は当時の話。
> - さらに Azure 系が `docingest.azure` プラグイン（`[azure]` extra）として追加された：
>   ① `engine: azure_di`（Azure Document Intelligence でクラウド解析 → docling-parse の
>   Windows OOM を回避）② `docingest export`（chunks → Azure AI Search へ自前 embedding で
>   投入、field_map で任意スキーマ対応）。
> - **大型 PDF の OOM 対策**として `engine: vision_only` も追加（docling 解析を完全に
>   スキップし、pymupdf レンダ + 全頁 Vision。実測 300 頁で docling は SIGSEGV 死、
>   vision_only は 87 秒で完走）。
> 以下の本文は歴史記録として残す。新しく判断するなら上のブロックを優先。

DocIngest の `providers.py` は **OpenAI 直連 / Gemini / Anthropic の 3 つ**しかない。
Azure OpenAI 接続用 `AzureOpenAIProvider` は無い。

```python
# DocIngest が用意する全 Vision provider
@dataclass class GeminiProvider:    provider: str = "google"
@dataclass class OpenAIProvider:    provider: str = "openai"
@dataclass class AnthropicProvider: provider: str = "anthropic"
# AOAI なし
```

**企業環境の典型的な要件**:
- 全 LLM 呼出を AOAI 経由で監査
- 1 つの Azure サブスクリプションに課金集約
- データレジデンシー（日本リージョン強制）
- VNet 内通信のみ許可

**現状の妥協**:
- OpenAI 直連 key を worker に secret として投入 → 企業要件と矛盾するが動く
- もしくは Vision を完全無効化（`MPLAT_DOC_VISION_PROVIDER=none`）→ 画像内容を失う

**長期対応**:
- DocIngest 上流 PR で `AzureOpenAIProvider` 追加（Anthropic を真似て）
- もしくは fork して内製
- litellm は `azure/<deployment>` model 名 + `api_base` で AOAI 対応なので、本体側に
  通せるレイヤーはある

### 4.2 子プロセス隔離は省略不可

DocIngest は docling / pypdf / litellm / Vision API 等の **C 拡張**を内部で動かす。
これは Python の `threading` では **絶対に中断できない**:

- thread に `ctypes.pythonapi.PyThreadState_SetAsyncExc` を打ち込んでも C 層で
  ブロック中は無視される
- DocIngest がハングした場合、API プロセスごと巻き込まれる
- 30 分のタイムアウト保護を効かせたいなら子プロセス化が必要

**Mplat の実装**: `_run_docingest_with_supervisor` (`job_handlers.py:139`) で
`multiprocessing.spawn` の子プロセスで実行 + 父プロセスが poll で監視 +
cancel/timeout 時に `Process.kill()` で SIGKILL。

### 4.3 子プロセスのログが消える ⭐ 2026-05-25 踩到

`multiprocessing.spawn` モードで起動した子プロセスの `stdout/stderr` は、
**Container Apps の az logs に出てこない**ことがある。

**症状**: prod で DocIngest が 0 件返してきたが、子プロセス内のエラーは log に
一切残らない。`Sanitize/Extract` も呼ばれず（empty text のため skip）、
表面上は「正常完了 0 件」と見える。

**対策**: 子プロセス内でログを `StringIO` に蓄積 → 結果と一緒に Pipe で
父プロセスに送る → 父プロセスが自分の logger に re-emit する。
こうすれば Container Apps log に確実に出る。

```python
# _docingest_worker 内
import io
log_buf = io.StringIO()
handler = logging.StreamHandler(log_buf)
logging.getLogger().addHandler(handler)
# ... DocIngest 実行 ...
conn.send(("ok", text, log_buf.getvalue()))   # ← ログを添付

# 父プロセス側
msg = parent_conn.recv()
for line in msg[2].splitlines():
    logger.info("[docingest-child] %s", line)
```

### 4.4 multiprocessing は Pipe を使う、Queue を使わない ⭐ 2026-05-25 踩到

`multiprocessing.Queue` は内部で feeder thread を持ち、`put` した大きな
payload を非同期で pipe に書込む。DocIngest が返す 100KB+ の Markdown を
Queue.put すると、worker が return しても feeder の join 待ちで
**`is_alive()` が永続 True のまま** になる（CPython の既知挙動）。

監視ループで `proc.is_alive()` を見ていると hang する → supervisor 機構が機能しない。

**対策**: `multiprocessing.Pipe(duplex=False)` を使う。Pipe の `send()` は同期
書込なので、worker が send 完了したら即時 exit できる。Mplat はこの方式に
切替済（commit 129c859）。

### 4.5 イメージサイズが 8-11GB

DocIngest を `pip install -e .` で入れると、依存解決で:

```
torch (CPU+CUDA)        ~ 500 MB
nvidia-cublas           ~ 420 MB
nvidia-cudnn            ~ 370 MB
triton                  ~ 200 MB
nvidia-nccl             ~ 200 MB
nvidia-nvshmem          ~  60 MB
（その他 cuda-* 群）
─────────────────────────────
合計                    ~ 1.5-2 GB が GPU 関連
```

docling が内部で torch を import するが、**実行時は CPU 推論**のみ。
GPU 依存は不要だが pip が拾ってしまう。

**対策候補**:
- `torch` を CPU-only build に固定（`pip install torch --index-url
  https://download.pytorch.org/whl/cpu` を Dockerfile に書く）
- DocIngest が `[gpu]` / `[cpu-only]` extras を提供してくれるよう PR
- 現状の Mplat worker image は 11GB のまま

### 4.6 build cache が命中しない

DocIngest を抱える Dockerfile は典型的に:

```dockerfile
COPY pyproject.toml ./
COPY src/mplat ./src/mplat        # ← src 変えるたび cache 失効
RUN pip install -e ".[azure]"      # ← 1.5GB の pip install が毎回走る
```

**業務コードを 1 行変えるたびに 8-10 分の rebuild**。

**対策**: 2 段 COPY:

```dockerfile
COPY pyproject.toml README.md ./
RUN mkdir -p src/mplat && touch src/mplat/__init__.py
RUN pip install -e ".[azure]"     # ← 依存だけ install、cache が効く
COPY src/mplat ./src/mplat         # ← src だけ後から COPY
```

もしくは uv + BuildKit cache mount（より速い）。

### 4.7 デフォルトで余計な LLM を呼ぶ

`config/default.yaml` は **chunking と knowledge_map がデフォルト enable**:

```yaml
chunking:
  enabled: true
  enrichment:
    contextual_summary: false   # これは default false
knowledge_map:
  enabled: true
  ai_summary: true              # LLM 1 call per knowledge base
```

`outputs=["markdown"]` を渡すと chunking.enabled は false に押し下げられるが、
**chunking_assist の LLM 呼出は内部で chunking 以外の段階でも走ることがある**
（境界推定）。default で **chunking_assist の LLM = gemini-3-flash-preview**、
GEMINI_API_KEY 無ければ fallback で gpt-5.4-mini。

**対策**: env で明示的に止める:

```bash
DOCINGEST__chunking__enabled=false              # 念のため
DOCINGEST__knowledge_map__enabled=false
DOCINGEST__quality_report__enabled=false
DOCINGEST__run_log__enabled=false
DOCINGEST__refine__enabled=false
DOCINGEST__chunking__enrichment__contextual_summary=false   # 既定 false だが念のため
```

Mplat ではこれらを **`docingest_adapter.py` の `_default_kwargs` 経由で
config_overrides として渡す**ことで一括無効化できる（今後の改善候補）。

### 4.9 異步 batch ingest の跨容器ファイル受渡し ⭐ 2026-05-25 踩到

**症状**: prod で `POST /api/ingest/batch` に PDF/xlsx を投入してもすべて
**「completed: 0 件」**。エラー無し、ログ無し（§5.1 で log 回収後ようやく
`DocIngest result: total_files=0` が出て発覚）。

**根因**: api と worker は **別の Container**（Azure Container Apps では
別の Pod）。api が `tempfile.mkdtemp` で **api 容器の `/tmp`** に書いた
ファイル path を payload に乗せて Service Bus に投入 → worker が拾った
path は **worker 容器には存在しない** → DocIngest が「ファイル無し」と
判定して 0 件返す。

設計時点では InlineJobQueue（同プロセス thread）しか想定していなかった。
Azure 経路（ServiceBus + 別 worker container）では path が一切共有されない。

**対策**: ファイル本体を**共有ストレージ経由**で渡す。Mplat はすでに
`UploadFileStore` Protocol を持っているので、それを再利用:

```python
# api 側 (api.py:1962)
for f in files:
    file_bytes = await f.read()
    meta = upload_file_store.save(tenant_id, f.filename, f.content_type, file_bytes)
    items.append({
        "type": "file_id",
        "file_id": meta.file_id,
        "filename": f.filename,
    })

# worker 側 (job_handlers.py:320)
if item.get("type") == "file_id":
    data = upload_file_store.read_bytes(item["file_id"], tenant_id)
    tmp_dir = tempfile.mkdtemp(prefix=f"mplat_job_{tenant_id}_")
    doc_path = str(Path(tmp_dir) / item["filename"])
    Path(doc_path).write_bytes(data)
    # ... DocIngest に doc_path を渡す ...
    # 後処理で shutil.rmtree(tmp_dir)
```

`BlobUploadFileStore` を使えば api → Azure Blob → worker で確実に届く。
旧式 `type=file` + path も後方互換で残す（InlineJobQueue 経路では今も有効）。

**チェックリスト**:
- api と worker が別プロセス/別コンテナの構成では、**ファイル本体を local FS で
  渡すジョブ payload を絶対書かない**
- 共有ストレージ Adapter（UploadFileStore / Blob / Files）を**job投入の前に**
  必ず構築し、payload には file_id だけ載せる
- worker 側は読込後に tmp dir に展開、処理後に `shutil.rmtree` で掃除

### 4.11 docling の OCR engine 不可用 → PDF が破滅 ⭐ 2026-05-25 踩到

**症状**: prod に PDF を投入すると "成功 0 件" だが、extraction_runs の record に
PDF 原始 bytes (`%PDF-1.4 ... /Type /Outlines ...`) が `input_text` として
記録されていた。sanitize がそれを LLM に喂すと**乱码が大量の `<REDACTED>` に
打码される + Azure OpenAI content_filter が `jailbreak detected: True` で 400 拒否**
される連鎖事故。

**根因チェーン**:

1. worker Dockerfile に **`onnxruntime` がインストールされていない**
2. docling は OCR engine を auto 選択するが、`onnxruntime` 無 → torch backend に
   fallback
3. torch backend は `.pth` model を runtime に download しに行く
   (`/opt/venv/lib/python3.12/site-packages/rapidocr/models/ch_PP-OCRv4_det_mobile.pth`)
4. runtime stage は **`USER mplat` (非 root)**、site-packages に書込権限なし
5. `[Errno 13] Permission denied` で docling 全体 parse fail
6. **しかし DocIngest は "successful=1" を返す**（fallback で原始 bytes を markdown
   に保存）→ Mplat 側は成功と判定 → sanitize → content_filter 400

**修正** (2026-05-25 commit):

```dockerfile
# Dockerfile.worker builder stage
RUN pip install --no-cache-dir -e ".[azure]" \
    && pip install --no-cache-dir -e /opt/DocIngest

# onnxruntime を別 RUN で追加。RapidOCR (docling の OCR) は onnxruntime backend
# を最優先で使う。model は包内同梱で runtime download 不要 → Permission denied
# 回避。
RUN pip install --no-cache-dir onnxruntime
```

**重要**: docling の "successful" は信用してはならない。DocIngest 結果 → markdown
の中身を必ず内容 sanity check する（§5.2 / §5.5）。

### 4.12 LLMSanitizer の chunk_size が対話想定で大文書に致命的 ⭐ 2026-05-25 踩到

**症状**: 38 万字の xlsx を ingest すると sanitize で 10 分超かかり、ユーザーが
中止せざるを得なくなる。Worker は何も悪くない（ひたすら AOAI を叩いている）。

**根因**: `LLMSanitizer.__init__` の `max_chunk_chars` 既定が **1500 字**（対話
の 200 字想定で設計）。38 万字 / 1500 = **257 chunk** × **2 LLM 呼出**（匿名化 +
verify）= **514 LLM 呼出**。4 並列でも 128 ラウンド、AOAI 1 呼出 ~5 秒 = **10 分**。

**修正** (2026-05-25 commit):

```python
# llm_sanitizer.py
max_chunk_chars: int | None = None,  # default 30000 (env MPLAT_SANITIZER_MAX_CHUNK_CHARS)
max_workers: int | None = None,      # default 4    (env MPLAT_SANITIZER_MAX_WORKERS)
enable_verify: bool | None = None,   # default True (env MPLAT_SANITIZER_ENABLE_VERIFY)
```

- chunk=30000 で 38 万字 → **13 chunk**（20× 削減）
- 余裕で 1 chunk = 15K token、gpt-5.4-mini の 200K context に収まる
- verify=false で更に半減（しかし精度落ちる）

**根本対策**: §4.13 で「sanitize 自体を skip 可能に」。大文書では sanitize 不要が
多い (社内文書)。

### 4.13 sanitize は ingest 既定 off にすべき ⭐ 2026-05-25 踩到

**症状**: 社内文書 (GenAI 受賞者名簿、設計書、運用ルール等) を ingest すると、
人名 / 内部システム名 / プロジェクト名がすべて `<PERSON_A>` / `<CLIENT_IT_A>` /
`<PROJECT_B>` 等のトークンに置換される → **skill の具体性が消える**、検索しても
「誰の」「どのシステムの」「どのプロジェクトの」runbook か分からない。

**設計判断**: sanitize は元々**対話 sanitize 用** (ユーザーがチャットで漏らす顧客
機密を匿名化)。**ingest 経路は内部文書なので sanitize 不要**。FlyWheelHook
(対話起源) は今まで通り sanitize on のまま。

**修正** (2026-05-25 commit):

- **後端**: `job_handlers.run_ingest_batch` で payload の `sanitize` flag を読む。
  未指定なら env `MPLAT_INGEST_SANITIZE_DEFAULT` (既定 **false**) に従う。
- **API**: `POST /api/ingest/batch` に `sanitize` form field 追加。
- **前端**: ナレッジ取込 UI に「サニタイズする」チェックボックス追加 (既定 off)。
  顧客機密含む文書のみ on にする。

```bash
# env で既定値変更可
MPLAT_INGEST_SANITIZE_DEFAULT=false   # 既定 (社内文書想定)
# MPLAT_INGEST_SANITIZE_DEFAULT=true  # 機密文書多い場合
```

**経路別 sanitize 真理表**:

| 経路 | sanitize default | 上書き可能か |
|---|---|---|
| 対話 (FlyWheelHook) | ✅ on (固定) | 不可（対話は常に on） |
| ingest (前端 batch UI) | ❌ off (既定) | ✅ チェックボックス |
| ingest (env override) | ✅/❌ | ✅ `MPLAT_INGEST_SANITIZE_DEFAULT` |
| ingest (API payload) | — | ✅ payload `sanitize: true/false` |

### 4.14 incremental cache が消える

DocIngest は `{output.dir}/.cache/*.meta.json` に「このファイルは前回処理済」
の証跡を残し、同一ハッシュなら処理を skip する。

**問題**: Container App が再起動すると、output.dir 配下が空になる → cache
ロスト → 同じファイルを再 ingest すると Vision を全部再呼出（コスト + 時間）。

**対策**:
- output.dir を Azure Files マウントに置く（Mplat は `mplat-files-vol` が
  ある、これに `.docingest_cache` を割当ればよい）
- もしくは Mplat 側の SkillStore で重複排除する（file hash → 既存 skill 検索）

## 5. ログ・診断システム（最重要）

DocIngest 周りの bug 解析は **「ログが見えない」が最大の敵**。何が起きたか
分からないまま「0 件抽出」だけ表面化する。以下の 4 つを必ず備えること。

### 5.1 子プロセスログを父プロセスへ回収する

**問題**: `multiprocessing.spawn` で起動した子の `stdout/stderr` は Container
Apps の `az logs` に出てこないことがある。子で `print` / `logger.info` しても
父プロセス・運用者からは見えない。

**実装**: 子プロセス内で `logging.StreamHandler(StringIO())` を root logger に
追加し、ログを bytes 列に蓄積。完了時に `conn.send(("ok", text, log_text))`
で結果と一緒に Pipe で父プロセスに送る。父プロセスは受取後、各行を自分の
logger に re-emit する（`[docingest-child] ...` プレフィックス付き）。

```python
# 子プロセス側
import io, logging
log_buf = io.StringIO()
handler = logging.StreamHandler(log_buf)
handler.setFormatter(logging.Formatter("%(asctime)s %(levelname)s [%(name)s] %(message)s"))
logging.getLogger().addHandler(handler)
# ... DocIngest 実行 ...
conn.send(("ok", text, log_buf.getvalue()))

# 父プロセス側
msg = parent_conn.recv()
if len(msg) >= 3 and msg[2]:
    for line in msg[2].splitlines():
        logger.info("[docingest-child] %s", line)
```

参考実装: `src/mplat/adapters/job_handlers.py` の `_docingest_worker` /
`_run_docingest_with_supervisor`（2026-05-25 追加）。

### 5.2 DocIngest 結果の構造を必ずログに残す

DocIngest が「成功した」と言っても `markdown_files` が空のケースが頻発する
（.txt、safety abort、形式判定ミス）。表面の戻り値だけ見ると区別できない。

**ログに残すべき項目**:

| 項目 | 何を見るか |
|---|---|
| `result.markdown_files` の件数 | 0 なら docling 解析が空 |
| `result.stats` 全体 | total_files / successful / failed / errors |
| `result.stats["safety"]["aborted"]` | safety threshold 超過で abort されたか |
| `result.output_dir` 配下のファイル一覧 | sources/*.md が無い理由を切分（解析失敗 vs 書込失敗）|

```python
logger.info(
    "DocIngest result: markdown_files=%d, safety_aborted=%s, stats=%s, output_dir=%s",
    len(result.markdown_files or []),
    bool((result.stats or {}).get("safety", {}).get("aborted")),
    {k: v for k, v in (result.stats or {}).items() if k in (
        "total_files", "successful", "failed", "total_tokens", "errors"
    )},
    result.output_dir,
)
# 出力ディレクトリ tree も最初の 20 件だけログに残す
for p in sorted(Path(output_dir).rglob("*"))[:20]:
    logger.info("output: %s (%s bytes)", p.relative_to(output_dir),
                p.stat().st_size if p.is_file() else "-")
```

### 5.3 環境変数の有無は子プロセス内で明示確認

子プロセスは parent の env を継承するが、Container Apps の secret が
**正しく注入されているか**は子プロセス起動後でないと確認できない。
特に `OPENAI_API_KEY` / `GEMINI_API_KEY` / `MPLAT_DOC_VISION_PROVIDER` は
DocIngest の挙動を大きく変えるので、子側で **bool 化してログに出す**:

```python
logger.info(
    "env check: OPENAI_API_KEY=%s GEMINI_API_KEY=%s MPLAT_DOC_VISION_PROVIDER=%s",
    bool(os.getenv("OPENAI_API_KEY")),
    bool(os.getenv("GEMINI_API_KEY")),
    os.getenv("MPLAT_DOC_VISION_PROVIDER", "(unset)"),
)
```

**注意**: 値そのものをログに出さない（API key 流出を防ぐ）。bool / "(unset)"
にとどめる。Mplat では一度 API key 全文がログに出てしまった事故あり、要注意。

### 5.4 Container Apps の `az logs` 取得の限界

- `--tail` は **最大 300**（それ以上は分割取得が必要）
- 1 リクエストで数百行の Azure SDK の HTTP DEBUG ログが混じると、業務ログが
  押し流される
- `--revision <name>` で revision 固定 + `grep` で絞らないと使い物にならない
- **Application Insights** に統合した方が長期的に楽（既に
  `APPLICATIONINSIGHTS_CONNECTION_STRING` 設定済なら Logs ブレードで検索可）

**典型コマンド**:

```bash
# DocIngest 関連だけ取得
az containerapp logs show -n mplat-worker-v2 -g <rg> --tail 300 \
  --revision mplat-worker-v2--0000017 --type console 2>&1 \
  | grep -E "docingest-child|DocIngest|Sanitize|Extract|WARNING|ERROR"

# 子プロセスログだけ
az containerapp logs show -n mplat-worker-v2 -g <rg> --tail 300 \
  --revision mplat-worker-v2--0000017 --type console 2>&1 \
  | grep "\[docingest-child\]"
```

### 5.5 「成功した、0 件」を warning にする

DocIngest が空 markdown を返した時、Mplat は `if not input_text.strip(): pass`
で sanitize/extract を skip して **status=done で 0 件返す**。これが
「処理は成功した」と見えてしまう。

**対策**: text_len=0 を WARNING ログに昇格 + extraction_runs の record に
`error: "empty markdown from DocIngest"` を残す。

```python
if not input_text or not input_text.strip():
    logger.warning("DocIngest returned empty text for %s (path=%s, size=%d)",
                   item_id, item.get("path"), file_size)
    item_error = "DocIngest returned empty markdown"
    # 以降の sanitize/extract は skip
```

これで `az logs | grep WARNING` で 0 件抽出の発生を即発見できる。

## 8. デバッグ checklist（0 件抽出が起きた時）

順番に確認:

1. **子プロセスのログは到着しているか**
   ```
   az containerapp logs show -n mplat-worker-v2 -g <rg> --tail 300 \
     --type console | grep "\[docingest-child\]"
   ```
   見えない → §5.1 の StringIO + Pipe 機構が動いていない

2. **Vision provider が初期化されたか**
   子プロセスログに `DocIngestAdapter built, vision_provider=...` が出る。
   `vision_provider=None` なら API key 未設定 or `MPLAT_DOC_VISION_PROVIDER=none`

3. **DocIngest が text_len 返したか**
   ログに `DocIngest returned: text_len=N`。
   - N=0 → 入力が読めなかった（safety threshold 超過 / 形式非対応 / 壊れたファイル）
   - N=数百 → docling が文字層だけ拾った（Vision が動いていない可能性）
   - N=数千〜数万 → 正常

4. **safety violation していないか**
   DocIngest の safety check（§ `safety.mode: warn`）に引っかかると spec を
   返さず exit する。大ファイル時は `acknowledge_large=True` 必要。

5. **API key の経路**
   ```
   env | grep -E "(OPENAI|GEMINI|AZURE_OPENAI)_API_KEY"
   ```
   AOAI key は DocIngest が認識しない（§4.1）。`OPENAI_API_KEY` / `GEMINI_API_KEY`
   のどちらかが必須。

## 9. やってはいけないこと

- ❌ **主プロセスで直接 DocIngest を呼ぶ**: HTTP リクエストハンドラ / 対話 API が
  ハングする
- ❌ **multiprocessing.Queue で 100KB+ 文本を渡す**: §4.4 で hang
- ❌ **Vision を切って OCR fallback に期待する**: DocIngest は OCR を持たない、
  Vision off = 画像系コンテンツ全部消える
- ❌ **prod の az logs だけで debug を完結させる**: §5.1 で子ログが消えるので
  まず子ログ回収機構を入れる
- ❌ **API key 全文をログに出す**: §5.3 — bool / "(unset)" にとどめる
- ❌ **Dockerfile で `COPY src/ ./src/` を pip install より前**: build cache が
  毎回ふっとぶ
- ❌ **`docker image prune -a -f` で「掃除」する**: tag 付き image も全部消える、
  build 後すぐにやると deploy が「tag does not exist」で死ぬ（2026-05-24 踩到）
